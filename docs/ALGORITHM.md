# ProjectionRoom 算法说明

本文只讲两件事：**数据是怎么从主播流到最深的叶子节点的**，以及**所有节点的播放进度是怎么对齐的**。
设计取舍的依据见 [`SPEC.md`](SPEC.md)；实测数据与验收工具见根目录 `README.md` 与 `tools/`。

---

## 0. 全局不变量

理解后面所有算法，只要抓住这 6 条：

| # | 不变量 | 违反后的现象 |
| :-- | :--- | :--- |
| I1 | **服务器不传输任何视频字节**。它只转发信令、分配拓扑、广播房间状态 | 一旦中继视频，成本模型崩塌（退回 CDN） |
| I2 | **主播是唯一时间权威**。进度只有主播产生，中继只转发、绝不改写 | 多个时间源 → 全房间来回跳 |
| I3 | **分片边界 = `moof` 边界**。固定字节切分会产生"半个 moof" | `appendBuffer` 直接抛错 |
| I4 | **写入 `SourceBuffer` 必须严格按序号、串行** | 乱序 append 报错或产生空洞 |
| I5 | **跳转必须"先补数据、后定位"**（`currentTime` 在空缓冲上会被丢弃） | 卡在旧位置，永远不动 |
| I6 | **没数据就不矫正、不起播**（加载不设超时） | 薄缓冲硬播 → 同步振荡，偏差放大数倍 |

## 1. 数据链路

### 1.1 全景

```
主播                                    服务器（无视频字节）              观众 A（一级）        观众 B（二级）
 │                                            │                              │                    │
 │ 1. segmenter 预处理 → init.mp4 + c*.m4s + index.json                       │                    │
 │ 2. media-index ──────────────────────────► │ 校验索引（media.Index.Validate）                    │
 │                                            │ 广播索引 ──────────────────► │                    │
 │ 3. join ──────────────────────────────────► │ 拓扑分配（§1.2）             │                    │
 │                                            │ parent-assignment ─────────► │                    │
 │ 4. WebRTC 直连（SDP/ICE 经服务器转发）       │                              │                    │
 │◄════════════════════ DataChannel ══════════╪══════════════════════════════╡                    │
 │ 5. have 位图（每 3s） ─────────────────────► │                              │ 转发 have ────────► │
 │ 6. req(idx) ◄──────────────────────────────┤  req(idx) ◄──────────────────┤                    │
 │ 7. 二进制帧(8B 头 + fMP4 片段) ────────────► │  二进制帧 ──────────────────► │                    │
 │ 8. progress（每 500ms，逐跳转发，不改写）───► │  ──────────────────────────► │ ─────────────────► │
```

### 1.2 拓扑分配（服务端，纯函数）

`internal/usecase.Assign` 是**确定性纯函数**：输入是参与者的实测上行、RTT、加入顺序与当前父节点，输出是全树分配。

```
                   ┌── K0 = floor(U × 0.8 / B) ──┐
                   │  U = 主播实测上行            │
                   │  B = 索引里的实测码率         │
                   └──────────────┬──────────────┘
                    K0 ≥ 2 ───────┴─────── K0 ≤ 1
                      │                     │
                 扇出模式                单链分发模式
          主播直连 K0 个一级节点     主播只连 1 个"分发节点 D"
                      │            （按实测上行选举 + 1.5× 换防滞回）
                      └────────┬────────────┘
                               ▼
                 广度优先铺开：**先按深度择父**（树越浅越好），
                 同深度再比：余量占比 0.5 / RTT 0.3 / 稳定性 0.2
                 分支上限 = floor(上行 × 0.8 / 码率)，深度 ≤ 4
```

两个刻意的设计：

- **排布容量与准入容量分开算**。未实测上行的节点按保守默认值参与排布（预热期也能建树），
  但**准入闸门只认真实测容量** —— 否则每个新节点都凭"默认 2 个位"再引入容量，房间会自我膨胀。
- **指纹去重下发**。`mode|distributor|primary|backups|children|depth` 组成指纹，
  只有变化才下发 `parent-assignment`，这正是"换防期间不强断连接"的前提。

### 1.3 逐分片取数：自适应条带化

客户端 `useTopology.pickParent(idx)` 的决策顺序：

```
第 1 步  这一片已经失败过？        → 按尝试次数轮转到下一个父节点（超时转投，L2）
第 2 步  有父节点明确声明拥有它？   → 主父拥有就用主父；否则在拥有者之间轮转（条带化，L1）
第 3 步  谁都没声明（位图未到）？   → 先问主父一次；失败即进入第 1 步的轮转
```

三个反直觉但必要的约束：

- **只问"明确拥有"的父节点**。位图是唯一依据。盲发给一个自己还在下载的节点，
  实测每次起播会刷出 30–80 次 `NOT_FOUND`。
- **主播的位图必须广告"全都有"**。主播是 Seeder，能按需读盘；只广告自己预取的窗口，
  启用"只问拥有者"之后，所有观众就再也不会向它要窗口外的分片 —— 直接卡死（真机踩过）。
- **主父积压才分流**（在途 ≥ 3）。这样条带化不会把分片丢给一个还没数据的备用父。

### 1.4 分片请求与转投

```
子节点                     父节点
  │ req{rid, idx} ─────────►│
  │                         │ 命中 → {t:'chunk', rid, idx} + 二进制帧
  │ ◄───────────────────────│ 未命中 → {t:'err', rid, idx, code:'NOT_FOUND'}
  │ 3s 超时 / 收到 err                                        │
  ▼                                                          ▼
在途表按 (peerId, idx) 建索引：同一片可向多个父并发请求，先到先用
超时/失败 → attempts[idx]++ → 下一次 tick 换下一个父节点
```

### 1.5 写入播放器：严格按序

`flushOrdered()` 维护一个"下一个待追加序号" `nextAppend`：

```
chunkStore 里 nextAppend 存在？ ──是──► appendBuffer(该片) → nextAppend++ → 再检查
                                └─否──► 等（后续到达会再次触发）
```

配套的三条：

- **init 段只追加一次**（它把 track 配置告诉 SourceBuffer），换缓冲不需要重发。
- **淘汰窗口**：默认丢弃 `nextAppend - 4` 之前的分片；**有子节点时保留 12 片**，
  否则转发节点自己刚丢掉的片，下游正要来取。
- **贪心预取窗口**：`[max(播放头, nextAppend), 播放头 + 30]`。
  起点不能低于 `nextAppend`（否则会把已淘汰的片反复重取，实测刷出上千次无谓交付）；
  终点必须以**播放头**为锚（以 `nextAppend` 为锚会让窗口一路前移，把整部片子拉完）。

## 2. 同步算法

### 2.1 时间基准与时钟估计

主播每 500ms 广播一次（新子节点接入时先连发 10 个样本加速收敛）：

```ts
progress { currentTime, hostClockMs, clockEpoch, seq, paused, rate }
```

- `hostClockMs` 是**主播的单调时钟读数**，逐跳原样转发，任何中继都不得改写（I2）。
- `clockEpoch` 是主播页面的随机纪元：主播一刷新页面 `performance.now()` 归零，
  观众必须**丢弃并重置滤波**，否则全房间一起跳到错误位置。
- `seq` 单调递增：乱序/重复的进度一律丢弃。

观众用**最小滤波**估计"我与主播时钟的偏移"：

```
每个样本  sample = localNow - hostClockMs     // 含正向延迟，恒 ≥ 真实偏移
offset = min(窗口内最近 30 个样本)             // 延迟最小的那次最接近真值
expected = playback.currentTime + (localNow - offset - hostClockMs) / 1000
```

**已知偏差（重要）**：最小滤波的估计误差 = 路径上观测到的**最小单向延迟**，
因此观众会稳定地比主播滞后这么多。直连时只有几毫秒；多一跳就多一份转发延迟，
实测深度 2 的叶子稳定滞后约 **350ms**（p95 327ms）。
正解是**逐跳时钟中继**：每个中继在转发的消息里带上"自己的本地时钟 + 自己到主播的偏移"，
子节点据此把"到父的偏移"与"父到主播的偏移"相加，误差从"整条路径的单向延迟"
降到"各跳半 RTT 之和"。这是下一步要落地的改动（见 §4）。

### 2.2 三级漂移矫正

```
每 100ms：drift = video.currentTime - expected

|drift| ≤ 0.10s        → playbackRate = 主播速率
0.10 < |drift| ≤ 0.50  → playbackRate = 主播速率 × 0.95 / 1.05   （无感，不打断缓冲）
0.50 < |drift| ≤ 1.50  → 跳缓冲内最近位置（不 seek，不清缓冲）
|drift| > 1.50s        → 清缓冲 + 补数据 + 重新定位（seekPipeline）
```

**速率是"主播速率之上的临时缩放"**，不是绝对值。曾经每条进度消息都无脑套用主播速率，
把同步环的 ±5% 微调每 500ms 冲掉一次 —— 偏差恒定卡在 ~490ms 永远修不回来。

### 2.3 跳转流水线（顺序不可颠倒）

```
清空缓冲(remove)  →  补齐目标分片（等它真的 append 进 SourceBuffer）  →  再设 currentTime
```

先清后设会失败：空缓冲上给 `currentTime` 赋值会被浏览器丢弃
（HTML 规范：`HAVE_NOTHING` 时只记录"默认起始位置"）。这个坑在真机上表现为
**主播和所有观众一起卡在旧位置**。

### 2.4 启动门控（加载不设超时）

新节点接入（或跳转）后不立即播放，而是进入"加载中"：

```
门控开闸条件（全部满足）：
  1. 已连续追加 ≥ 4 片
  2. 目标位置前方已缓冲 ≥ 8s（跳转后为 4s）
  3. 时钟偏移估计已收敛：样本 ≥ 6 且最小值 ≥ 0.8s 没再下降
开闸动作：在**已有缓冲内**定位到权威位置并播放（不清缓冲）
```

- **不设超时**：上游没数据就一直是"加载中"，并在等待超过 20s 时提示"上游带宽可能不足"。
  宁可让用户看到等待，也不要薄缓冲硬播 —— 后者会立刻触发大幅矫正，
  把偏差从几十毫秒放大到几百毫秒（实测开闸第一帧 −387ms）。
- **预取按门控目标**：门控期间播放头还停在 0，必须按权威目标位置预取，
  否则会从 0 拉一堆永远不会播的分片，而起播位置一直没有数据。
- **追加游标跟着门控目标走**：否则 `flushOrdered` 会一直等一个不会被取到的分片。
- 门控期间**只更新权威状态，不动播放器**（不响应暂停/跳转）。

### 2.5 中继节点的三条职责

1. 把收到的 `progress` / `time-sync` **原样转发给子节点**（不改 `currentTime`/`hostClockMs`/`seq`）。
2. 自己按 §2.2 同步播放（中继也是观众，标准与叶子一致）。
3. 从自己的分片仓库应答子节点的请求（缺片就回 `NOT_FOUND`，让子节点转投）。

## 3. 关键时序

### 3.1 新节点接入

```
新节点                服务器                 父节点(上游)              其他节点
  │ join ────────────►│                                                      │
  │                    │ 重算拓扑（§1.2）                                     │
  │ ◄─ joined（含 mediaIndex / 当前播放状态 / 容量）                          │
  │                    │ parent-assignment ──►│（children 变化时）            │
  │ ◄─ parent-assignment                      │                              │
  │ 连主父 + 备用父                             │                              │
  │                                                  ──► 指纹变化者收到新分配  │
  │ ── 进入门控（加载中，不设超时）──────────────                              │
  │ ◄─ have 位图 / progress 连发样本 ──────────│                              │
  │ req(目标分片…) ───────────────────────────►│                              │
  │ ◄─ 二进制帧                                │                              │
  │ 攒够 4 片 + 8s + 时钟收敛 → 开闸播放 ───────                              │
```

### 3.2 慢父节点（抗慢节点）

```
子节点窗口 [P, P+30]
   ├─ 主父份额：正常时全部走主父
   ├─ 主父在途 ≥ 3 或某片失败 → 转投"明确拥有该片"的备用父
   └─ 单片 3s 超时 → attempts++ → 下一次换下一个父节点
效果：一个慢父节点只拖慢它那一份；实测限速到 1Mbps 时子节点仍能在数秒内
      从备用父补齐（形态验证见 tools/verify-m3.mjs 的 --throttle）。
```

## 4. 已知问题与下一步

| # | 问题 | 影响 | 计划 |
| :-- | :--- | :--- | :--- |
| P1 | 多跳叶子的时钟偏差 = 路径最小单向延迟 | 深度 2 稳定滞后 ~350ms（仍在 500ms 内） | 逐跳时钟中继（§2.1） |
| P2 | 门控开闸第一帧仍有 ~60–150ms 瞬态 | 个别运行里 max 会逼近 500ms | 开闸后再给 1s 稳定期，用缓冲内跳转而非重灌 |
| P3 | 深度 2 叶子起播期有 ~60 次 `NOT_FOUND` | 浪费一轮 RTT，被门控掩盖 | 接入时先向 Seeder 拉一次全量位图再开始取数 |
| P4 | 多个 Chrome 同机运行时 MediaSource 偶发被平台关闭 | 已自愈（调度器重新挂载），但会丢一次缓冲 | 追踪触发条件；必要时改为重建 MediaSource 而不只是重挂载 |
| P5 | 分发节点换防、限速隔离的真机验收未跑 | M3 验收 C/D 未闭环 | `tools/verify-m3.mjs` 已支持 `--uplink` / `--throttle` |
